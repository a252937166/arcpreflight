# Known limitations

Written for the `SUBMISSION_RESTRICTED` profile at code baseline `8c59d10` (the former `360f086`; commit identities (email and, for early commits, name) were corrected on 2026-10-07, trees unchanged). Update it when behaviour or evidence changes.

## What the output means

- ArcPreflight reports **observations at a pinned block** and the result of deterministic checks. `NO_POLICY_VIOLATION` means *no configured check fired at that block* — it is **not** a safety rating, an audit, or a guarantee about the target.
- There is no security score, no audit, no custody of customer funds, and no on-chain enforcement. The SDK is not an enforcement boundary.
- The read-to-sign gap cannot be removed. Final validation at a fresh block narrows the window but is not atomic. The final-validation snapshot must not precede the service-fee confirmation block or any confirmed state change required by this execution, and it must independently satisfy the configured freshness limits. A recent fetch timestamp does not make an old block fresh. If no suitable snapshot is available, the run waits within a bounded deadline or pauses; stale state is never silently substituted.
- A baseline is only as good as the person who approved it. The service does not judge whether the approved business choice is sensible. Same implementation hash does not imply the same risk: dependencies and storage state outside the checked scope can still change. At final validation the caller must re-fetch and verify the approval content referenced by this intent, including its current validity and revocation status; an intent bound to approval A never inherits a later approval B — a new approval is a new baseline digest that requires the intent and check records to be rebound and re-evaluated, and it never overwrites the original report chain.
- The checks constrain the supported signer path under a trusted application process. They do not provide on-chain enforcement or protection against compromise of that process or its keys.

## Scope

- **One decision-eligible template:** an OpenZeppelin ERC-1967 UUPS proxy (v5.4.0) in front of the demo merchant, with one method, `pay(orderId)`. Other contracts are raw observations with `decisionEligible=false`, including Circle's GatewayWallet and FxEscrow, which are observed but not supported for decisions.
- **The demo is self-contained.** It runs on the project's own fixtures with the project's own wallets. A purchase by a tester is a tester's purchase, not agent adoption. No external customer, revenue or repeat usage is claimed.
- **Evidence status** is in [EVIDENCE.md](EVIDENCE.md) and [ACCEPTANCE.md](ACCEPTANCE.md). Until the mainnet rows there say otherwise, everything that exercised payments and business transactions ran on testnet or in mocks.

## Wallets and signing

- Two executing signers exist, both on the fixed fixtures only: the project's own demo-runner key (runner mode) and, since design v3.3 (2026-10-08), the visitor's own non-delegated EOA through its browser wallet (wallet mode). Smart accounts (ERC-1271/4337), EIP-7702 delegated accounts and MPC or custodial wallets as a signer are not supported in either mode: at validation the payer account must carry no code.
- **Wallet mode has a weaker pre-send guarantee than runner mode, by construction.** The service validates the exact plan for the wallet payer at a fresh pinned block and records the attempt before the wallet is prompted, but it never sees the signed bytes: whatever the wallet actually sends is compared with the plan **after** it is visible on the chain (`to`, `data`, `value`, `chainId`, type must agree; wallet-set gas, fees and nonce are recorded as deviations). A wallet that signs something else produces a `MISMATCH` record, not a prevented transaction; the order state then decides whether the order was paid. There is nothing to rebroadcast: recovery works from the reported hash, the order state and the merchant's `OrderPaid` event (bounded log search), and an attempt whose hash was never reported is recovered through that event or closed `NOT_SENT` after 24 h. The browser remembers the attempt id before prompting the wallet; a visitor whose browser storage is cleared mid-way can still recover through the session that owns the attempt, and a lost session leaves the attempt to the worker (chain facts are still recorded; the private passport is no longer reachable).
- **Order identity before the send.** Every order the service creates is written `PLANNED` before `createOrder` leaves, `SENT` with the hash, `CONFIRMED` after the receipt. A creation interrupted in between is reconciled from the chain (`CONFIRMED` when `getOrder` finds it, `UNKNOWN_CREATION` after a 10-minute window otherwise) and never replaced inside the same admission. Rehearsed on testnet 2026-10-08 (`evidence/selftest/testnet-lifecycle-2026-10-08T10-50-41-609Z.json`); mainnet evidence pending.
- The wallet mode in an intent is declared, and the policy rejects anything but `EOA_DIRECT_NON_DELEGATED`. The pre-signing account check of spec §6.4 is implemented for the controlled P0 signer (2026-10-07): at final validation the runner requires a local key adapter whose address equals `intent.from`, reads the account's code at the validation snapshot (`eth_getCode`, pinned by block hash) and refuses delegated or contract code or an inconclusive read; after signing, type, chainId, to, data, value, nonce, gas, both fee fields, access list and authorization list are compared with the plan. Project ownership of the key is not what is relied on — the on-chain state is. No smart-account support was added; the boundary already chosen is enforced. Verified by runner tests and by the 2026-10-07 testnet rehearsal (three real code reads at the validation snapshot, none inconclusive); mainnet evidence pending.
- The Developer page signs the x402 fee authorization in the browser and, in wallet mode, asks the wallet to send exactly the validated plan (`eth_sendTransaction`; the wallet owns the nonce). Wallet support is limited to injected EIP-1193 providers discovered through EIP-6963 (MetaMask, OKX Wallet, Rabby, Coinbase Wallet and Brave extensions; a legacy `window.ethereum` fallback); there is no WalletConnect, no mobile deep link and no custodial connector. Disconnecting revokes the site's `eth_accounts` permission where the wallet implements `wallet_revokePermissions` and clears the page state otherwise — a wallet that ignores the revocation keeps the site connected on its own side. Account and chain changes are followed through the provider's events; the multi-wallet picker and the revocation were exercised against fake providers in tests, not against every real extension.
- The `walletEvidenceDigest` in execution receipts is the evidence digest of the real `eth_getCode` read at the validation snapshot. If that read fails, the digest is a marked `INCONCLUSIVE` placeholder and nothing is signed.

## Operations

- **Keys on the server.** The API process holds the runner key, the merchant key (which also relays check-fee settlements and pays their gas) and a narrowly scoped order-creator key: the DemoMerchant `orderCreator` role can only create orders. The deployer-admin key (upgrade, pause, withdraw) is loaded only as a fallback when no order-creator key is configured, with a start-up warning and an `adminKeyInProcess` flag in `/v1/network`; it is meant to stay on an operator machine. The testnet fixtures were redeployed with the role on 2026-10-07; since the 2026-10-08 redeploy the public testnet preview runs those fixtures with the order-creator key on the server and the owner key removed from it (`adminKeyInProcess = false` on the public `/v1/network`). Separate keys in one process are separate roles, not independent protection against compromise of that process. Balances are capped by design: a few USDC in total, topped up by hand. Small balances reduce exposure; they do not turn application-level budgets into chain-enforced limits.
- **Read routes never broadcast (v3.2 §10.2).** `GET /v1/demo/runs/{id}` and `GET /v1/requests/{id}` only read chain facts (receipt, order state, nonce, settlement logs) and may record what they read; they never submit a new or previously signed transaction. Sending happens only in the start-up pass, the recovery worker (every `RECOVERY_INTERVAL_MS`, default 30 s), the `POST /v1/demo/run` pre-run gate, `POST /v1/preflight`, and the two authorized recovery commands `POST /v1/demo/runs/{id}/recover` (requires the admission's `clientRunRequestId`) and `POST /v1/requests/{id}/recover` (owner principal). Verified by API tests; a browser prefetch or a polling agent therefore cannot cause a broadcast.
- **Admission identity (v3.2 §10.1).** `POST /v1/demo/run` requires a `clientRunRequestId` (16–128 chars). It is bound, in the admission transaction, to the run it admits: the same key returns the original run (200, `admission: "existing"`), the same key with another scenario is `409 RUN_CONFLICT`, and a lost response therefore never starts a second order. The key is also the capability for the recovery command, so it is unguessable by construction (the web app uses `crypto.randomUUID()` and keeps it in local storage). It is not an identity: anyone holding the key can read and recover that run.
- **Same-nonce replacements.** When the signed hash never receives a receipt but the signer nonce was consumed, the reconciler identifies the consuming transaction by a bounded binary search over `eth_getTransactionCount` at block numbers (from the head block recorded at the broadcast marker). If that transaction pays the same order, the attempt closes as `SUPERSEDED` with business success attributed to the named replacement and the original hash `UNKNOWN`; if it does not, the attempt closes `NOT_MINED` with the order read as unpaid; if the node cannot serve the history, the attempt **stays open** with the note "could not be identified" and nothing is guessed — a consumed nonce alone never closes an attempt (fixed 2026-10-08 after a testnet run was wrongly closed `NOT_MINED` by a lagging node of the load-balanced public RPC: the nonce query reached a fresh node while the receipt and order reads reached a stale one; the fixed rule closes `NOT_MINED` only from an identified consuming transaction whose receipt is visible and does not pay the order, closes `CONFIRMED` when the block scan finds our own hash and its receipt, and waits when the receipt still lags or when a node's facts contradict each other). The same rule applies to wallet attempts. An unreadable order state concludes nothing. Nothing is ever re-signed by reconciliation.
- **Two networks, two instances.** The public site serves Arc mainnet at the root and Arc testnet under `/testnet` from two instances of the same bundle with separate databases; the web app's switch only changes its API base path, explorer, wallet chain and per-network local storage, and every label comes from the instance's reported network, never from the path. Records do not cross: a testnet run is a testnet fact and shows as such; the testnet side spends the project's testnet funds only. Both instances load the same key files (the same addresses exist on both chains) — nonces are per chain, so the single-sender rule holds per network.
- **Single instance, single sender.** One Node process per network with SQLite on one small server. No high availability; a restart interrupts a run in flight (the run is recorded and the budget it reserved stays consumed). The reference CLI (`examples/merchant-agent`) uses the same demo-runner and order-creator keys as a local API would: never run it against the same network while an API process holding those keys is executing a run. The relayer's in-process nonce lock is acceptable only for this deliberately single-process release and is not, by itself, sufficient across restarts, overlapping deployments or maintenance scripts. Operating constraints: one active sending process per relayer address; no overlapping old and new senders during deployment; durable transaction and nonce state; start-up reconciliation before new sends; no concurrent manual transactions from the same account (the probe script must not run while an API holds the same key on the same network).
- **Crash window (spec D07) — implemented 2026-10-07, mainnet evidence pending.** The signed business transaction is persisted (encrypted at rest) with its hash, nonce, order id, labels and the approval/report/validation digests, then a durable "broadcast may be attempted" marker is written, then the bytes are sent. A crash or receipt timeout after the marker leaves the run `RECONCILE_REQUIRED` (its receipt reads `UNKNOWN`) — never a business failure. At start-up and on demand, reconciliation works only from the original hash and the order state: a receipt yields `CONFIRMED`/`REVERTED` plus the order read-back; a transaction whose nonce was consumed by something else is closed as not executed; a transaction signed but never marked is closed as never sent; a dropped transaction is re-broadcast byte-identically only inside its validation window and otherwise waits until its nonce is consumed. Recovery never creates an order, buys a check or signs a replacement, and a new run is refused while an earlier transaction is unresolved inside its window. Residual: the frozen 1.0 `ExecutionReceipt` schema has no "not mined" chain status, so a transaction proven unminable is recorded as `UNKNOWN` with `businessStatus = NOT_EXECUTED` and a note. Verified by runner and API fault-injection tests; the 2026-10-07 testnet rehearsal took three real business transactions through persist → mark → broadcast → reconcile (all `CONFIRMED`, orders read back as paid) and a restart on the same database found nothing open — no crash was injected on the live chain, so the crash windows themselves rest on the fault-injection tests; mainnet evidence pending. Payment (x402) recovery is a separate path and is implemented and tested.
- **Payment Passport (format 1.0, `docs/PASSPORT.md`).** A passport is a portable, read-only evidence export of one workflow: the referenced approval, the records, the correctly attributed USDC costs and the chain facts a separate process can check with an Arc RPC and trusted approval anchors. It is not a token, an identity credential, a guarantee or a bearer authorization; importing one enables no signing or broadcasting. The verifier reports findings, never one overall PASS: without anchors the approval source is `UNVERIFIED`, without an RPC the chain checks are `UNVERIFIED`, and `CURRENT_ELIGIBILITY` is never evaluated — a historical success does not authorize a new payment. A complete rewritten passport with recomputed hashes is not proof of original approval; a transaction hash is not proof of service delivery; a current contract balance is not proof that this order was paid. The export never contains the fee authorization's signature (the fee transaction's calldata is redacted to its keccak), raw signed transactions, keys or encrypted payloads. A client-side expiry of a signed business transaction is not an on-chain revocation: the bytes stay isolated and confidential even when the application will no longer submit them.
- **Public execution gate (`PUBLIC_EXECUTION`).** On the mainnet instance, `POST /v1/demo/run` and `POST /v1/wallet/attempts` answer `503 EXECUTION_GATED` until the operator sets `PUBLIC_EXECUTION=1` (together with `MAINNET_VERIFIED=1`, cutover step `open`) after the mainnet acceptance and lifecycle rehearsals passed; the acceptance scripts pass the gate with the operator's admin token so the gate cannot block the evidence it waits for. Checks, orders, recovery, history and passports are never gated; the testnet instance defaults to open. `/v1/network.access.publicExecution` and `.walletExecution` report the live state, so the site can say "gated" instead of failing.
- **What recovery may conclude (review round 2).** An `OrderPaid` event alone never closes a wallet attempt: the paying transaction's body and receipt must be fetched, its fields compared with the validated plan (`MISMATCH` when they deviate) and the order read at its block; otherwise the attempt stays open with a note. A consumed nonce alone never closes anything either (above). The reference CLI records its orders before the send like the API (`orders` table in its store, reconciled from the chain at every start).
- **Submission uncertainty is durable (review round 3).** The browser records on the server that the wallet was asked to sign (`POST …/prompt`) before the prompt and when the wallet answers with anything that is not a rejection; such an attempt is reconciled from the chain before anything else may be signed, across page refreshes, and the only actions offered are Recover and an explicit "I rejected it — abandon". A receipt without the transaction body never closes an attempt (the plan comparison is completed first). Late fee relay receipts are backfilled on closed attempts. The reference CLI persists every artefact and step as it runs (`runs`, `artifacts`, `run_steps` in its store) and exports a passport from them. The browser side of this was exercised with the injected test wallet (fault modes) and two live testnet attempts, not yet with a real wallet extension; the manual pass in `docs/WALLET-CHECKLIST.md` remains open. After the review of `0c0d406`: the marker is an exclusive claim (one grant per attempt; other tabs reconcile), the wallet's account, chain and the clock are re-read after the claim and the request is bound to the plan's `chainId`, and every runner send is preceded by a fresh clock read. What remains inherent is the gap between the page's last read and the wallet's own send: a wallet that ignores `chainId` and switches networks inside that gap is outside the service's control, and the after-the-fact plan comparison records what was actually sent.
- **Evidence before the broadcast.** A run whose artefacts cannot be persisted stops before the broadcast marker with nothing sent; after the send a persistence failure is logged and the record is rebuilt from the store and the chain. A run interrupted after the store recorded a closed outcome is closed from the store at the next reconciliation pass, so the run record, the page and the passport cannot disagree with the store.
- **Validation window.** `finalValidation.expiresAt` counts from the pinned observation (`snapshot.observedAt + maxFinalValidationAgeSeconds`), not from the end of the RPC reads; a validation whose snapshot already aged out is refused. In wallet mode the usable prompt window is therefore `60 s − the time the validation itself took` (a few seconds; up to ~25 s when the head had to advance past the fee confirmation).
- **Report lifetime.** A delivered report is usable for 300 s after its pinned observation (`REPORT_TTL_SECONDS`; it was 60 s before 2026-10-08). The longer window exists for the human-paced wallet workflow and is safe to the extent that the final validation re-reads the critical state at a fresh block before any execution; the decision's other inputs (signals, simulation) are as old as the report. The runner's own policy still refuses a report older than 60 s.
- **Open self-service (user decision 2026-10-08).** Any visitor's browser obtains an anonymous session (`POST /v1/session`, hashed server-side, 10 new sessions per client per day) and buys checks with its own wallet on either network; design v3.2 §6 had kept paid access to configured principals. Bounds: 200 checks per principal per day, the relayer balance floor and per-settlement fee cap, the daily developer-order budget (count + gas reservation) and the 45 s per-client cooldown. The visitor pays the fee; the project's exposure per check is the relayer's gas (≈ 0.0025 USDC on testnet observations, covered by the 0.01 USDC fee) and, for a developer order, the order-creation gas. A session token in a browser's local storage is the only key to that browser's history, recovery and private passports: clearing storage loses it (configured principals are unaffected).
- **Testnet faucet.** The testnet instance pays 0.2 testnet USDC per claim from the order-creator key (one claim per wallet and per client every 24 h, 30 per day, floor 1 USDC) so a visitor's wallet can pay the check fee and a small business amount; the route answers 404 on any chain other than 5042002.
- **Labelled interruption (Live Demo).** `interruptAfterBroadcast` makes the project runner stop waiting right after the send — the controlled experiment of design v3.2 §5 Moment B. The step is labelled `interruptedAfterBroadcast` and the UI says "simulated"; the recovery worker (or an observe read that sees the receipt) resolves the run from the original hash and the order state. Because the read route observes, a browser polling the run often sees the resolved state within seconds; the interruption is still real for the process that stopped waiting. Rehearsed on testnet 2026-10-08 (`recovered-confirmed`, nothing added by recovery); mainnet evidence pending.
- **Verifier semantics (fixed 2026-10-08).** `FEE_ATTRIBUTION` now decodes the fee transaction's calldata and requires every authorization field (from, to, value, validAfter, validBefore, nonce) to equal `payment.json`, and the capture's `inputKeccak256` to equal the fetched calldata; `COST_STATEMENT` recomputes the whole statement (totals, fee equivalence, authorized maximum, sources) and fails on any difference; history a node cannot serve is `UNVERIFIED` with the reason, never `FAIL`. Before this fix a modified validity window or a wrong total could verify PASS and an archive-less node produced a false FAIL; passports exported before 2026-10-08 are unaffected in content, only the verifier's judgement of them changed.
- **Reference CLI.** `examples/merchant-agent` runs the same business loop with a durable SQLite execution store; it records its order only after the creation receipt (the identity-before-send order store of design v3.3 is implemented in the API service; CLI parity is a follow-up, so a CLI process stopped between `createOrder` and its receipt leaves no local order row — the chain still has the order, and the CLI never pays an order it did not record). Its store keeps the signed bytes encrypted with a key derived from the runner key, and its `reconcile` command resolves open attempts from the original hash, nonce and order state; it refuses to start a new purchase while an earlier attempt is unresolved inside its validation window, and it refuses the owner key for order creation (the `orderCreator` role is required). `--crash-after-broadcast` ends the process right after the broadcast marker and the send — the controlled interruption of the recovery rehearsal; use it only against your own testnet fixtures.
- **Demo budget.** One live run at a time, 40 per day, 45 s per-client cooldown, and a runner balance floor. Default monetary caps per UTC day: 1 USDC of business payments, 0.40 USDC of check fees, 0.50 USDC of gas ceilings (createOrder ≤ 150k and pay ≤ 80k gas at ≤ 40 gwei). Monetary caps per cost category (business payments, check fees, gas) are configured reservations computed from the per-run amounts and are separate from the run count — 40 positive runs × 0.05 USDC would be 2 USDC in gross business payments before check fees and gas; this is a configuration calculation, not observed expenditure. Budget reservations are atomically committed before any external operation that may incur a charge. Repeated requests resolve to the same reservation and execution record. When a limit is hit, the demo page falls back to recorded samples, which are labelled `RECORDED_SAMPLE`.
- **Retention.** Quotes promise at least 30 days of recovery. Nothing deletes data after that yet. Public observation is limited to a short curated list, but each new observation is still stored as a public report (about 12 KB) and old rows are not pruned. Pruning is planned.
- **Network.** Arc's public RPC is load-balanced; reads are pinned `PIN_LAG` (8) blocks behind head and verified by block hash. A single RPC provider is trusted; digests detect later tampering with stored evidence but do not prove the provider was honest. Deterministic replay of a receipt chain requires the relevant schemas, methodology, adapters, policy, baseline and raw evidence — not just the hashes; hash consistency does not prove that an RPC provider supplied truthful state. A blocked request stops at its stage; no signing or broadcast records are manufactured.

## Dependencies

- **Check-fee settlement (self-relayed EIP-3009).** The project's merchant account submits each buyer's `TransferWithAuthorization` to the USDC contract and pays the gas in USDC. Low relayer balance (floor default 0.05 USDC) stops new quotes and broadcasts. Previously accepted authorizations remain durably recorded and recoverable. Payments that may already have been submitted continue through reconciliation. A per-settlement fee cap (default 0.005 USDC) refuses to relay when the estimated gas cost exceeds it — on testnet a settlement used ≈ 87k gas (≈ 0.0018 USDC at the 20 gwei floor), so with the 1.2× gas limit the cap trips above roughly 48 gwei and payments then wait as unresolved rather than being relayed at that price. *Paid* is established from the complete payment relationship, not from two matching event names in one receipt:

  | Layer | Required match |
  |---|---|
  | Application context | Authenticated principal, original request, immutable quote, and unique authorization mapping |
  | Authorization | Network, asset contract, payer, recipient, amount, validity bounds, and authorization nonce |
  | Transaction outcome | A successful receipt on the expected network |
  | Payment evidence | Events from the correct emitter, with fields attributable to that exact authorization and transfer |

  The `authorizationState` boolean alone is never proof — it is also true after a cancellation. Native and ERC-20 event accounting are kept separate: Arc's EIP-7708 `Transfer` logs emitted from the system address are ignored and only logs emitted by the USDC contract count, so one transfer cannot be counted as two payments. Execution by a third party is accepted only for a direct USDC authorization call whose calldata and receipt match the stored authorization; an unrecognised wrapper or an ambiguous event combination remains pending reconciliation rather than being accepted through loose log matching. If no evidence can be located, the payment stays unresolved and recoverable through the authenticated request endpoint rather than being marked paid; a cancelled authorization is marked failed and the report is not delivered. The one authorization → one quote → one report binding remains required; moving settlement in-house does not replace it. Check-fee settlements made before this change went through a hosted facilitator; those payment rows keep their original reconciliation path.
- **Arc public RPC** and the Arc explorer are third-party services.
- **The guided walkthrough is per browser tab.** Which checkpoints a visitor already inspected (order, check, payment, explorer) is remembered in the page's state only; a reload starts the walkthrough again for the same run. The run itself, its origin label and its outcome come from the records. The canvas lifecycle needs a 2D canvas; where it cannot draw, at phone width, or with reduced motion, the CSS lifecycle list carries the same stages.
- **Project funds are watched, not refilled.** The API's worker reads the project keys' balances every five minutes, logs once when a key drops below its threshold (`FUNDS LOW …`), and reports the reading on `/v1/network.funds` (Evidence page table; a warning on the Live Demo). Topping a key up is a manual operator action: nothing claims from any faucet or moves funds on a schedule.
- **Spend limits are layered, not one ledger.** Transactions a script signs (deployment, funding, the relay probe, the lifecycle's visitor key) are capped per transaction and per step by the spend guard, gas included. Spends the API makes on the operator's behalf (orders, check fees, runner payments, relays) are capped per transaction by the server's gas ceilings and per day by its reservations, and the acceptance scripts stop on the measured outflow of the project keys. The sum of the step caps is the plan's maximum; there is no single cross-step counter.
- **Release label = last code commit.** Docs-only commits after a release keep its label; `ops/deploy.sh` refuses to deploy with uncommitted code or fixtures, so the label always names the deployed code.
