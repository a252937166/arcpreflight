# Release capability manifest — `SUBMISSION_RESTRICTED`

> **Status: DRAFT, not frozen.** This describes what the code at baseline `8c59d10` (the former `360f086`; commit identities (email and, for early commits, name) were corrected on 2026-10-07, trees unchanged) implements, plus the docs in this folder.
> It becomes the release record only at the freeze step: set `releaseSha`, re-run the acceptance record
> ([ACCEPTANCE.md](ACCEPTANCE.md)) against that SHA, and confirm the live `/health/live` reports the same SHA.
> As of 2026-10-09 the public site runs the **testnet preview** of `3c1726b` (design v3.3 + review rounds 2 and 3 + the review of `0c0d406`, `ops/testnet-preview.sh`); the Arc mainnet cutover has not happened yet.

Closing a capability here means the server route, principal check and signer path reject it — not that a button is hidden.

## Supported subjects and methods

- **Decision-eligible intents:** `DemoMerchant.pay(orderId)` on the two configured DemoMerchant proxies (`SUPPORTED_TARGETS`), action `MERCHANT_PAY`, the deployment's own chain id.
- **Proxy template:** `oz-erc1967proxy-uups` v5.4.0 (`OZ_ERC1967Proxy_UUPS`, known proxy code hash in `fixtures/adapters.json`). Anything else is observed raw.
- **Public observation** (`OBJECT_OBSERVATION`: raw reads at a pinned block, `decisionEligible=false`) is limited to the curated list in `/v1/network` `observableSubjects`: the five external samples on mainnet (USDC, Circle GatewayWallet, StableFX FxEscrow, CCTP TokenMessengerV2, ERC-8004 IdentityRegistry) and the configured fixture proxies. Other addresses are refused, so the public report list stays a set of reviewed samples. External objects observed so far are listed in [EVIDENCE.md](EVIDENCE.md).
- **Checks:** `INTENT_BINDING`, `AMOUNT_SEMANTICS`, allowlists, `BASELINE_STATUS`, `EXECUTION_IDENTITY`, `CALL_SIMULATION`, `EVIDENCE_FRESHNESS`, plus Arc runtime advisories (`basis: network_advisory`).
- **Settlement backend:** self-relayed EIP-3009 — the merchant account submits the buyer's `TransferWithAuthorization` to the USDC contract and pays the gas in USDC; the buyer needs no gas for the check fee. This covers the check fee only; the business payment is the agent's own transaction. Low relayer balance stops new quotes and broadcasts. Previously accepted authorizations remain durably recorded and recoverable. Payments that may already have been submitted continue through reconciliation. One authorization → one quote → one report remains required. Legacy payment rows settled earlier through a hosted facilitator keep their original reconciliation path.
- **Keys:** the API loads a narrowly scoped order-creator key (DemoMerchant `orderCreator` role, create orders only) and falls back to the deployer-admin key only when none is configured (start-up warning; `adminKeyInProcess` in `/v1/network`). The deployer-admin key (upgrade, pause, withdraw) is meant to stay on an operator machine. Testnet fixtures redeployed with the role on 2026-10-07; the public preview runs them since 2026-10-08, with the order-creator key on the server and the owner key off it.

## Wallet paths

| Path | State |
|---|---|
| x402 payer: non-delegated EOA signing an EIP-3009 `TransferWithAuthorization` (EIP-1193 provider on the Developer page, or a local key) | supported for every session and configured principal; browser wallets discovered through EIP-6963 (MetaMask, OKX Wallet, Rabby, Coinbase Wallet, Brave extensions) with a legacy `window.ethereum` fallback; automatic chain switch, reconnect after refresh; disconnect revokes `eth_accounts` where supported |
| WalletConnect, mobile deep links, custodial connectors | not supported |
| Business execution: the project's own demo-runner EOA, EIP-1559 type-2, signed locally after final validation, on the fixed fixtures only | supported (`executionMode: runner`) |
| Business execution: the visitor's own non-delegated EOA through its EIP-1193 wallet (`eth_sendTransaction` of the validated plan), on the fixed fixtures only | supported (`executionMode: wallet`); validation for the wallet payer is server-side; the account must carry no code at the validation snapshot; field agreement is checked after the fact |
| MPC or custodial wallets (for example Circle's Agent Wallet) as signer | not supported |
| Smart-account (ERC-1271/4337) buyers, EIP-7702 delegated accounts | closed |
| Browser-wallet business execution | open (wallet mode, above) |

Record the values actually deployed at freeze. The relayer's in-process nonce lock assumes a deliberately single-process deployment: one active sending process per relayer address, no overlapping old and new senders during deployment, durable transaction and nonce state, start-up reconciliation before new sends, and no concurrent manual transactions from the same account. The checks constrain the supported signer path under a trusted application process; they do not provide on-chain enforcement or protection against compromise of that process or its keys.
